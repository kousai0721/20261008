# CLAUDE.md

## Project Overview

このプロジェクトは、Claude Codeを利用してAI-DLC
（AI-Driven Development Life Cycle）の開発プロセスを実践し、
Claude CodeおよびAI駆動開発に関する知見をチームへ共有するための
検証・学習プロジェクトです。

単にAIにコードを生成させることを目的とせず、
要求整理、設計、実装、テスト、運用検討までの開発ライフサイクルを通して、
AIと人間がどのように協働できるかを検証します。


## Goals

このプロジェクトでは、以下を目標とします。

- Claude Codeの基本操作を習得する
- Claude Codeを利用した開発フローを経験する
- AI-DLCのInception / Construction / Operationを一通り経験する
- AIが得意な作業と人間が判断すべき作業を整理する
- AIへ与えるコンテキストの設計方法を学ぶ
- 有効だったプロンプトや指示方法を記録する
- AIによる誤判断や過剰実装などの失敗例を記録する
- セッション間のコンテキスト引き継ぎ方法を検証する
- 最終的にチーム向けの知見として文書化する


## Repository Structure

リポジトリの基本構成は以下とします。

```text

├─ frontend/
├─ backend/
├─ memo/
├─ aidlc-docs/
│  ├─ inception/
│  ├─ construction/
│  ├─ operation/

frontend/
フロントエンドのソースコードを配置します。
backend/
バックエンドのソースコードを配置します。
memo/
個人の学習メモ、一時的な調査結果、コマンドの記録などを配置します。
memo/ の内容はAI-DLCにおける正式な成果物とはみなしません。
aidlc-docs/
AI-DLCの各工程で作成された正式な成果物を配置します。
前工程の成果物は、次工程における正式なインプットとして扱います。
Development Process
このプロジェクトでは、以下の工程を基本とします。
1. Inception
2. Construction
3. Operation
4. Retrospective
工程を機械的に守ること自体を目的とはせず、
開発対象や状況に応じて必要な作業を判断します。
ただし、重要な判断や工程の変更は人間の承認を得てください。
AI-DLC Working Principles
Human Responsibility
AIは開発作業を支援しますが、
最終的な意思決定、レビュー、承認の責任は人間が持ちます。
AIは以下について独自に重要な決定を行わないでください。
- 要求・仕様の追加や変更
- ユーザーが明示していないビジネスルール
- アーキテクチャ上の重要な判断
- 技術スタックの最終決定
- セキュリティに関する判断
- 外部システムとの契約変更
- データモデルの重要な変更
- 破壊的な操作
Ask Before Assuming
要求、仕様、設計に不明点や複数の選択肢がある場合は、
独自に補完せず、人間へ確認してください。
質問が成果物内に必要な場合は、以下の形式を使用してください。
[Question]
質問内容

[Answer]


人間から回答が得られるまでは、
その判断を前提とする後続作業を進めないでください。
Plan Before Execution
まとまった作業を開始する場合は、
原則として最初に作業計画を作成してください。
計画にはチェックボックスを使用してください。
例:
- [ ] Step 1: 要求を確認する
- [ ] Step 2: 不明点を整理する
- [ ] Step 3: 成果物を作成する
- [ ] Step 4: 整合性を確認する

計画を作成した時点では、
原則として実行を開始せず、人間のレビューと承認を求めてください。
承認後、計画に従って作業してください。
各ステップが終了した場合は、
チェックボックスを更新してください。
Review Cycle
基本的な作業サイクルは以下とします。
AIが計画する
    ↓
人間がレビューする
    ↓
人間が承認する
    ↓
AIが実行する
    ↓
AIが結果を報告する
    ↓
人間がレビューする

大量の変更を一度に行うのではなく、
人間がレビューできる単位で作業してください。
Documentation Policy
Language
AI-DLC関連のドキュメントは原則として日本語で記載してください。
ソースコード上の識別子や、
一般的に英語で記述される技術用語についてはこの限りではありません。
Official Artifacts
正式なAI-DLC成果物は aidlc-docs/ 配下に配置してください。
工程ごとの基本的な保存先は以下です。
Inception
aidlc-docs/inception/

以下のような成果物を必要に応じて作成します。
- ユーザーストーリー
- 受け入れ基準
- Unit of Work
- コンテキストマップ
- システム間・ユニット間の契約
- その他Inceptionで必要になった成果物
成果物のファイル名や数を事前に固定する必要はありません。
作業内容に応じて必要な成果物を提案し、
人間の承認を得て作成してください。
Construction
aidlc-docs/construction/

以下のような成果物を必要に応じて作成します。
- ドメインモデル
- 設計資料
- 実装計画
- アーキテクチャ検討
- 非機能要件
- テスト計画
- その他Constructionで必要になった成果物
Operation
aidlc-docs/operation/

以下のような成果物を必要に応じて作成します。
- デプロイ方法
- 設定管理
- 起動・停止方法

- 監視
- 障害対応
- バックアップ
- セキュリティ
- 保守・バージョンアップ
- その他運用に必要な成果物
Retrospective
aidlc-docs/retrospective/

以下を記録対象とします。

- AIが誤解した内容

- セッション切り替え時の気付き

- チーム開発に適用する際の考察
memo and aidlc-docs
memo/ と aidlc-docs/ は明確に区別してください。
memo/
→ 個人用メモ
→ 学習記録
→ コマンドメモ
→ 調査途中の内容
→ 一時的な情報

aidlc-docs/
→ AI-DLCの正式成果物
→ 人間とAIが合意した内容
→ 次工程への正式なインプット
→ チームへ共有可能な内容

AI-DLCの正式な判断や仕様を memo/ の情報だけに依存させないでください。
Inception Rules
Inceptionでは、
「何を実現するのか」を明確にすることを優先してください。
この段階では可能な限り、
- プログラミング言語
- フレームワーク
- データベース製品
- クラウドサービス
- その他具体的な実装技術
の選択を急がないでください。
最初にビジネス上の要求、ユーザーの目的、
ユーザーストーリー、受け入れ基準などを明確にしてください。
必要に応じてユーザーストーリーをUnit of Workへ分割してください。
Unit of Workの分割では、
高い凝集性と低い結合度を意識してください。
DDDの考え方は必要に応じて利用できますが、
DDDを適用すること自体を目的にはしないでください。
Construction Rules
Constructionでは、
Inceptionで合意された成果物を正式なインプットとして使用してください。
まずドメインやビジネスロジックを理解し、
その後で実装方法を検討してください。
設計段階でコード生成を要求されていない場合は、
コードを生成しないでください。
技術選定を行う場合は、
候補を比較し、メリット・デメリットを提示してください。
最終的な技術判断は人間に委ねてください。
Implementation
コード実装時は以下を守ってください。
- 一度に必要以上のコードを生成しない
- 実装計画に沿って小さな単位で実装する
- 既存コードを確認してから変更する
- 既存の設計・コーディングスタイルを尊重する
- 要求されていないリファクタリングを勝手に行わない
- 要求されていない機能を追加しない
- 不要な抽象化を増やさない
- 必要以上に複雑な設計を導入しない
- 標準ライブラリや既存ライブラリで十分な場合は再利用する
Testing Rules
実装完了だけを作業完了とはみなしません。
実装内容に応じて適切なテストまたは動作確認を行ってください。
テスト計画を作成する場合は、
要求や受け入れ基準との対応を明確にしてください。
必要に応じて以下を検討します。
- Unit Test
- Integration Test
- API Test
- E2E Test
- 受け入れ基準に対する確認
テスト失敗時は、
原因を調査せずにテストを無効化したり削除したりしないでください。
Operation Rules
Operationでは、
システムを「作って終わり」にせず、
実際に運用する場合に必要な事項を検討してください。
必要に応じて以下を扱います。
- 起動・停止
- デプロイ
- 設定
- 環境変数
- ログ
- 監視
- 障害対応
- バックアップ
- セキュリティ
- バージョンアップ
本番環境への変更やデプロイなど、
外部環境へ影響する操作は、
人間の明示的な承認なしに実行しないでください。
Context Management
AI-DLCでは、
前工程の会話そのものではなく、
前工程で作成・承認された成果物を次工程への正式なコンテキストとして扱います。
工程が切り替わる場合や、
会話コンテキストが大きくなった場合は、
新しいClaude Codeセッションへ切り替えることを検討してください。
新しいセッションでは、
過去の会話内容を推測せず、
リポジトリ内の成果物を読み直して状況を把握してください。
Session Handover
セッションを切り替える必要がある場合は、
必要に応じて HANDOVER.md を作成してください。
引き継ぎ資料には以下を含めてください。
- プロジェクト概要
- 現在のAI-DLCフェーズ
- 完了済み作業
- 未完了作業
- 人間が行った重要な意思決定
- 参照すべきファイル
- 現在の問題・制約
- 次に行うべき作業
- 新しいセッションで使用する最初のプロンプト
引き継ぎ後は、
新しいセッション側で関連成果物を読み直してから作業してください。
Git Rules
工程の区切りや、
意味のある作業単位でコミットすることを推奨します。
コミット前には変更内容を確認してください。
Claude CodeがGit操作を行う場合、
破壊的な操作やリモートへ影響する操作は
人間の承認なしに実行しないでください。
特に以下は勝手に実行しないでください。
- git push
- git push --force
- git reset --hard
- git clean
- ブランチ削除
- 履歴を書き換える操作
Security Rules
以下をソースコード、ドキュメント、Git管理対象へ保存しないでください。
- パスワード
- APIキー
- アクセストークン
- AWSアクセスキー
- 秘密鍵
- その他の認証情報
認証情報の利用方法が不明な場合は、
独自に判断せず人間へ確認してください。
外部サービスへコード、仕様書、ログなどを送信する必要がある場合も、
許可されているか確認してください。
Destructive Operations
以下のような破壊的または影響範囲の大きい操作は、
必ず人間へ確認してください。
- ファイルやディレクトリの大量削除
- DBデータの削除
- DBスキーマの破壊的変更
- クラウドリソースの削除
- 本番環境への変更
- Git履歴の破壊
- 大量の依存ライブラリ変更
Claude Code Learning
このプロジェクトでは、
成果物だけでなくClaude Codeの利用方法自体も検証対象です。
作業中に以下のような知見が得られた場合は、
Retrospective用の情報として記録してください。
- 有効だった指示方法
- 不明瞭だった指示
- Claudeが誤解した指示
- コンテキスト不足による問題
- 過剰なコンテキストによる問題
- セッション分割の効果
- CLAUDE.mdの効果
- 人間によるレビューが必要だったポイント
- AIに任せやすかった作業
- AIに任せるべきではないと感じた作業
Final Deliverable
この検証の最終成果物として、
以下のテーマのチーム共有用ドキュメントを作成します。
「Claude CodeでAI-DLCをやってみた」
最終ドキュメントでは、
少なくとも以下を整理します。
- 検証目的
- AI-DLCの概要
- 検証環境
- 開発対象
- 実施した開発プロセス
- Inceptionで実施したこと
- Constructionで実施したこと
- Operationで実施したこと
- Claude Codeの利用方法
- 有効だったプロンプト・指示方法
- 人間とAIの役割分担
- 良かった点
- 問題になった点
- 改善案
- チーム開発へ適用する場合の考察
事実として確認できた内容と、
今回の検証から得た考察は区別して記載してください。
